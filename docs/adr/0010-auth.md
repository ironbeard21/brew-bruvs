# 0010. Authentication: local accounts plus optional OIDC

- Status: Accepted (through P0-11)
- Date: 2026-11-21

## Context

Self-hosters need simple accounts out of the box, and many already run single sign-on (Authentik, Authelia, Keycloak). Phone apps need long-lived sessions.

## Decision

Local email-and-password accounts with a first-run admin setup, plus optional OIDC login configured by environment variables. Sessions stored in Postgres; phone apps use revocable tokens. Personal API tokens with scopes for integrations.

**Library: a minimal session layer of our own, plus `openid-client` (MIT) for OIDC.** Better Auth was evaluated and not chosen:

- Its routes are registered outside `@hono/zod-openapi`, so sign-in would be missing from the generated OpenAPI spec and the app's typed client (ADR-0005).
- It brings its own user, session and account tables and id conventions, which clash with UUIDv7 ids and global `uri` columns (ADR-0006).
- What we need is small: password hashing with Node's built-in scrypt, random tokens stored as SHA-256 hashes, and one table of tokens. That is a few hundred lines we fully control and test.

Details:

- Passwords: scrypt (N=2^15, r=8, p=3), salted; unknown emails are checked against a dummy hash so timing doesn't reveal accounts.
- One `auth_tokens` table holds web sessions (cookie, 30 days), app tokens (bearer, until revoked) and personal API tokens (bearer, `read` or `read`+`write` scope). Only hashes are stored; a token is shown once.
- `SIGNUP_MODE=open|invite`. Invites are one-time codes created by admins, valid for 7 days.
- OIDC: authorization code + PKCE. An identity signs into its linked account, else the account with the same email if the provider says the email is verified, else a new account. The admin chose to trust the provider, so OIDC sign-in is not limited by `SIGNUP_MODE`.

## Consequences

Works with no external services; SSO users can plug in their provider. Every auth route is in the OpenAPI contract. We own the security-sensitive code, so it needs review and tests: login rate limiting and password reset are not built yet and are tracked as follow-ups.
